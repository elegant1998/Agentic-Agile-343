## 序言：从“氛围编程”到“验证工程”的范式跃迁 (From Vibe Coding to Verified Engineering)
AI Coding 已经显著提高代码生成、检索、修改和测试执行的速度，但速度并不自动等于正确交付。当 Agent 的执行速度超过人类的验证速度，组织更难回答三个问题：它理解对了吗？它越界了吗？它凭什么可以上线？

“氛围编程（Vibe Coding）”适合探索，却不能直接承担严肃交付。更强的模型面对模糊意图、缺失约束和宽松验收时，仍可能更快地产生偏离。当前研究与工程实践共同指向一个更稳健的结论：Agentic 系统的效果不仅取决于模型能力，也高度依赖规格、上下文、工具权限、验证、恢复和流程控制。

因此，我们提出 **Agentic Agile（智能体敏捷）**：一种面向 AI 研发的人机协同治理框架。它以意图为方向，以约束为边界，以 Agent 为执行能力，以证据支持裁决，以遥测推动持续改进。它不主张让 AI 无条件接管研发，也不要求组织彻底放弃现有敏捷与 DevOps，而是把适合机器执行的工作放入可验证、可恢复、可追责的控制系统。

## 一、理论基石：构建于三大科学领域的第一性原理

Agentic Agile 并非管理学的生搬硬套，它的底层逻辑是对认知科学、控制论与系统论在 AI 时代的第一性原理进行深度重构。

### 1. 认知科学（Cognitive Science）：突破“碳基认知带宽”极限
*   **第一性原理**：人类大脑的工作记忆（Working Memory）存在严苛的容量瓶颈（米勒的魔法数字 7±2），且跨个体协同受制于邓巴数（Dunbar's Number，即人类智力允许维持的稳定社交网络联系人数上限，150人限制）。
*   **传统机制的价值**：WIP 限制、任务分解和可视化管理帮助人类降低认知负担、暴露等待，并没有因为 AI 出现而失效。
*   **Agentic 启示**：把检索、生成、比较、测试和重复执行外化给机器，让人类把有限注意力集中在目标、边界、异常和责任判断。Agent 可以降低部分协调成本，但不会消除上下文、冲突和沟通损耗，因此仍需要明确的编排、交接和验证机制。

### 2. 控制论（Cybernetics）：从阶段反馈到高频机器控制回路
*   **第一性原理**：控制论奠基人诺伯特·维纳指出，一切稳态系统的维系必须依赖“反馈机制”来消除偏差系统，且控制系统的精准度直接取决于反馈周期的短频与摩擦力。
*   **传统机制的边界**：站会、评审和回顾适合承载人的信息同步与价值判断，但若测试、约束和异常只能等到会议才被发现，反馈就会滞后。
*   **Agentic 启示**：把可自动化检查嵌入执行过程，使生成、测试、诊断和修复形成秒级至分钟级的快速内环；把生产质量、成本和价值信号通过遥测反馈到下一轮意图、约束和编排，形成慢外环。机器反馈补强人的判断，而不是取消所有人类节奏。

### 3. 系统论（System Theory）：用受控多样性应对系统复杂性
*   **第一性原理**：依据系统论学者阿什比提出核心理论——阿什比法则（Ashby's Law of Requisite Variety，即“只有多样性才能吸收多样性”），控制系统的多样性能力必须等于或大于被控对象的复杂多样性。
*   **传统机制的价值与边界**：分解、WIP 限制、模块隔离和同步节奏仍然能够控制复杂性，但在人力成为验证瓶颈时，响应速度和并发能力受到限制。
*   **Agentic 启示**：多 Agent、工具和并发算力可以吸收部分执行复杂性，前提是任务依赖、权限、状态、冲突和退出条件被显式编排。算力不会消灭业务与系统复杂性；没有 Graph、Harness 和独立验证，并发只会更快地放大错误。

## 二、核心哲学：Agentic Agile 宣言

沿着 2001 年《敏捷软件开发宣言》重视价值、反馈与适应的精神，我们提出面向智能体时代的五条价值主张。我们承认右侧内容仍有价值，但在 AI 研发治理中更重视左侧内容：

1. **意图锚定（Intent Anchoring）** 胜过 详尽规约（Detailed Specifications）
   *(人类负责定义为什么做、什么结果值得接受；机器可以补充细节，但关键规格仍必须可判定)*
2. **多模态涌现协作（Multimodal Emergent Swarming）** 胜过 跨职能人类团队（Cross-functional Teams）
   *(让专业 Agent 承担可并行、可验证的执行，减少低价值信息搬运；跨领域价值冲突仍由人裁决)*
3. **算法规则与架构韧性（Algorithmic & Arch Resilience）** 胜过 流程纪律与仪式（Process & Ceremonies）
   *(把安全、权限、质量和恢复要求转成机器可执行门禁，同时保留明确的责任人和例外机制)*
4. **实时遥测与闭环对抗（Real-time Telemetry & Adversarial Loop）** 胜过 阶段性复盘（Retrospective Meetings）
   *(用持续运行信号补强阶段性复盘，让问题更早暴露，并由证据支持改进)*
5. **基于验证的系统工程（Verified Engineering）** 胜过 随性提示与氛围编程（Prompting & Vibe Coding）
   *(探索可以开放，交付必须回到契约、约束、独立验证、证据和责任签署)*

## 三、结构剖析：Agentic Agile 的“3-4-3 治理架构”

Agentic Agile 的落地骨架是**“3个超级角色、4个动态工件、3大自治运行机制”**。它不以取消多少会议衡量先进程度，而以价值责任是否清楚、边界是否可执行、结果是否可验证来判断治理是否有效。

### 📌 3 个超级角色 (The 3 Roles)
在 Agentic Agile 中，价值责任、治理责任和执行责任被明确分开。小团队可以一人兼任多个角色，但同一高风险事项的提出、执行和验证不应完全失去制衡。

1. **意图主理人（Intent Owner, IO）**
   * **前身**：Product Owner (PO) / 业务发起人
   * **重塑**：不必亲自规定每个实现步骤，但必须明确业务目标、非目标、成功标准和风险偏好，并对最终 Intent Contract 进行显式签署。Grill-Me 可以帮助澄清，不能替 IO 作出价值决定。
2. **编排架构师（Orchestrator Architect, OA）**
   * **前身**：Scrum Master (SM) / 架构师 / PMO
   * **重塑**：从“管人”变为“管机器”。OA 不再以“写 Prompt”的熟练度定义价值，而是承担真正的 **Agentic Engineering（智能体工程）**职责：设计契约机制、维护约束矩阵、编排运行时工作流、分配 Agent 算力（Token 预算），并在系统出现漂移、死循环或证据不足时进行治理介入。
3. **自治蜂群（Autonomous Swarm, AS）**
   * **前身**：开发、测试、运维、设计等跨职能 Scrum 团队
   * **重塑**：由开发、测试、安全、运维或领域 Agent 组成的受约束执行网络。底层模型仍具有概率性，Skill、Context、Graph、Harness 和验证体系用于提高行为稳定性，并让失败能够被发现、停止、恢复和追责。

### 📌 4 个动态工件 (The 4 Artifacts)
四大工件不是为了增加文档，而是把方向、单次承诺、边界和裁决依据外化为人和机器都能使用的治理资产。

1. **意图图谱（Intent Graph）**
   
   * **定位**：连接战略目标、用户价值、能力、任务、依赖、约束、状态与证据的宏观导航地图。它可以与 Product Backlog 共存，也可以用 Markdown、YAML、数据库、需求平台或图数据库实现；核心是关系可追溯，而不是必须采用某种 Graph-RAG 技术。
   
   * **示例形态**：不再是 `作为用户，我想要...以便于...` 的孤立卡片，而是系统可解析的节点网络：
     
     ```mermaid
     graph TD
        A[战略北极星: 闪电贷上线且单笔欺诈损失<50元] --> B(业务图谱: 闪电贷核心交易流)
        A --> C(硬性约束: 信用分低于700直接熔断)
        A --> F(用户画像: 25-35岁/信用分700+/高频网购偏好)
        F --> B
        B --> D{当前状态: Dev-Agent 实时推演中}
        C --> E[历史上下文: 关联2025年3月大面积反欺诈攻击复盘]
     ```
     
   * **生成机制 (How it is Generated)**：
     
     * **多源输入**：可以从战略、PRD、业务规则、代码现状、运行事件和访谈中提取候选节点。
     * **人机共建**：Agent 可以辅助解析、连线和发现冲突；IO/OA 对目标、范围和关键关系负责。自动生成的关系在验证前只能标记为候选，不能直接成为业务事实。
    
2. **意图契约（Intent Contract）**

   * **定位**：从意图图谱中为一次具体任务裁剪出的可签署执行基准，明确目标、非目标、验收标准、风险边界、依赖和验证方式。
   * **产生机制**：OA 运用批判性思维识别歧义、伪需求和激励冲突，通过 Grill-Me 逐条帮助 IO 决策；完整契约必须由 IO 本人显式签署，OA 和 Agent 不得代签。
   * **治理意义**：它回答“这一次究竟承诺什么”，避免全局愿景直接落到代码，也避免 Agent 把探索性对话误当成实现规格。

   <img src="./pic/image-20260727160212126.png" alt="意图契约示例" style="zoom:50%;" />

3. **约束矩阵（Constraint Matrix）**
   
   * **定位**：把权限、质量、安全、合规、成本、性能、环境、升级和恢复要求分为 MUST/SHOULD/MAY，并尽可能转成可执行门禁。仓库级指令和 AI Coding Guide 可以帮助注入约束，但不能代替工具权限、测试、策略引擎和恢复机制。
   * **示例形态**：部署在 Agent 运行沙箱周边的 YAML/JSON 配置文件（Guardrails）：
     
     ```yaml
     # 智能体全局约束矩阵 (Harness Guardrails)
     budget_limits:
       max_tokens_per_intent: 500,000
       max_adversarial_loops: 5  # 防止红蓝对抗陷入死循环
     compliance_red_lines:
       forbidden_modules: ["db.drop", "payment.bypass"]
       data_privacy: "MASK_ALL_PII" # 强制敏感数据脱敏
     escalation_protocol:
       # 突破预算或触碰法务禁区时，立即阻断并呼叫 OA/IO 裁决
       trigger_human_in_the_loop: TRUE 
     ```
4. **证据包（Evidence Bundle）**

   * **定位**：按同一个 Contract ID 汇聚 AC、MUST、测试、代码差异、人工审查、风险、回退、Token 和遥测摘要，支持批准、条件批准、补证、拒绝、撤回或升级等裁决。
   * **治理意义**：测试全绿只是证据之一。Evidence Bundle 让责任人能够区分已经证明的、尚未证明的和明确接受的风险，并将发布结论绑定到当前代码、环境和版本。

**涌现式增量**是四大工件共同治理后产生的可交付结果，不是治理工件本身。**Telemetry** 则是贯穿图谱、契约、约束和证据的反馈系统：每个契约形成一份任务级遥测与 Dashboard，所有任务再聚合为项目级 Dashboard，推动下一轮意图、约束和编排改进。

### 📌 3 大自治运行机制与 SCOPE-V 控制回路

三大自治机制不是放任 Agent，而是在不同时间尺度上控制偏差：LOOP-1 检查产出是否与当前契约自洽；LOOP-2 在授权范围内根据测试与约束失败诊断、修复和重试；LOOP-3 将经过验证的经验反馈到图谱、约束、知识、记忆、测试和 Skill。SCOPE-V 为三个 LOOP 提供持续运行的控制面。

1. **LOOP-1 自洽（Self-Consistency）与契约前置门**
   
   * IO 可以用自然语言、图表或业务材料表达初始意图。OA 通过批判性思维和 Grill-Me 将探索性对话逐步转成可判定契约。只有当目标、非目标、AC、风险和约束足以支持执行，并由 IO 显式签署后，任务才进入 Orchestrate。执行前和每个关键微检查点，Agent 都要复述目标、影响范围与停止条件，检查产出是否仍与契约自洽。
2. **LOOP-2 自愈（Self-Healing）与高频验证闭环**
   * 大模型不可避免会犯错。Dev、QA、安全或验证 Agent 可以在沙箱中生成、测试、批判和修复，形成 P ⇄ E 的快速内环；但模型自评不能作为唯一成功证明，关键结论仍需真实测试、工具结果和独立验证。
   * **SCOPE-V 不是六步瀑布流程，而是六个持续运行的控制面**：Specification 定义方向，Constraints 守住边界，Orchestration 管理依赖与权限，Proof 产生证据，Evolution 根据失败修复与学习，Verification 独立裁决。人类可以退出边界清晰的逐步执行，但在价值判断、不确定验证和不可逆操作处重新进入。
3. **LOOP-3 自进化（Self-Evolution）、遥测反哺与人类裁决**
   * 经过验证的失败、修复和生产遥测可以回写意图图谱，并提出约束、测试、知识、记忆或 Skill 的候选更新；未经证据支持的模型反思不得直接成为组织规则。
   * 以下情形必须触发 HITL：价值目标或风险偏好冲突；不可逆操作；权限越界；证据不足；预算或重试超限；法律、伦理与业务责任无法由规则裁决。系统暂停相关分支，由 IO、OA 或指定责任人处理。
   * 人类裁决以 Evidence Bundle 为主要输入，而不是只看 Agent 的自然语言总结。OA 检查证据链，IO 或授权责任人决定批准、条件批准、补证、拒绝、撤回或升级，并明确范围、有效期和回退条件。

### 📌 Harness Engineering：让治理要求进入运行时

3-4-3 只有进入 Harness 才能从方法主张变成工程控制。六大支柱共同回答 Agent 看什么、能做什么、按什么顺序做、记住什么、如何被评估以及失败后怎样恢复：

| 支柱 | 核心问题 | 典型资产 |
| :--- | :--- | :--- |
| Context | Agent 应该看到什么 | 图谱、契约、代码切片、AI Coding Guide |
| Tools | Agent 能触达什么 | Tools Manifest、最小权限、调用审计 |
| Graph | 任务怎样编排 | Work Graph、依赖、并发、Handoff |
| State & Memory | 状态和经验怎样延续 | Loop Memory、检查点、冲突与衰减 |
| Evaluation & Observation | 怎样判断做得对不对 | 测试、Evidence Bundle、Telemetry、Dashboard |
| Constraints & Recovery | 什么不能做，失败后怎么办 | Harness 门禁、HITL、回退、重调度 |

Harness 不取代 CI/CD、测试平台和安全工具，而是把契约、权限、门禁、证据和恢复嵌入现有工程系统，使 Agent 无法仅凭自然语言声明“已经完成”。

## 四、范式协同：Agentic Agile 在什么条件下补强传统敏捷？

基于前置的系统复杂性理论，**阿什比法则（Ashby's Law）**指出：“只有多样性才能吸收多样性”。
传统敏捷通过小批量、WIP 限制、反馈、协作和持续改进控制不确定性，这些原则仍然重要。但当“需求变化快、验证可自动化、上下文规模大、机器可并发执行”时，部分控制职责可以从会议和个人纪律迁移到契约、Harness、自动验证和遥测。Agentic Agile 不是对所有场景的统一替代，而是对 AI 执行速度下研发治理方式的补充与重构。

| 方法论/框架 | 仍然有效的核心 | 在 AI Coding 场景下的新边界 | Agentic Agile 的补强方式 |
| :--- | :--- | :--- | :--- |
| **Scrum** | 目标聚焦、短周期反馈、跨职能协作 | Agent 可以在一个 Sprint 内完成大量变化，固定节奏可能晚于机器反馈 | 保留价值与责任节奏，将任务级验证和状态更新转为事件驱动 |
| **Kanban** | 可视化流动、限制 WIP、管理阻塞 | Agent 并发增加后，瓶颈常从编码迁移到上下文、测试和审批 | 用 Work Graph、并发预算与遥测观察新的系统瓶颈 |
| **XP** | TDD、重构、持续集成和技术纪律 | 人工持续执行纪律的成本较高，Agent 也可能绕过宽松测试 | 将 TDD、静态检查和回归固化进机械门，并保留独立验证 |
| **SAFe / LeSS** | 跨团队对齐、依赖和组合管理 | 多层信息搬运无法跟上高频 Agent 执行 | 用图谱、跨模块协议和证据聚合减少重复同步，战略与风险决策仍由人负责 |

## 五、落地演进阶梯：组织如何向 Agentic Agile 跃迁？

没有企业能一键切换到 100% 的智能体敏捷。我们定义了组织的 **四阶段自治成熟度模型（Autonomy Maturity Model, AMM）**。

### 5.1 四级总览

成熟度不应给整个企业贴一个单一标签。一个团队可能在测试生成上达到 L3，在生产发布上维持 L2，在业务价值判断上始终保留人类裁决。等级必须按任务类型、风险等级和能力维度分别评估；自治升级需要同时满足能力、验证、恢复和责任四类门槛。

| 等级   | 名称                               | 一句话                           |
| ------ | ---------------------------------- | -------------------------------- |
| **L1** | 工具依附期（Copilot Agile）        | AI 是个人外骨骼                  |
| **L2** | 人机编队期（Hybrid Agentic Scrum） | AI 是可派发任务的虚拟同事        |
| **L3** | 受控自治期（Constrained Autonomy） | 3-4-3 接管边界清晰、可验证的工作 |
| **L4** | 适应性治理期（Adaptive Agentic Governance） | 意图驱动闭环，人批核心策略与风险 |

------

### 5.2 L1：工具依附期（Copilot Agile）

- **现状**：保持现有 Scrum / Kanban / 瀑布式等流程基本不变。协作、排期、验收仍依赖人工会议与人工文档。

- **动作**：引入代码补全、需求/文档草稿生成、单点问答。AI 附着在**单个员工**身上，是效率外骨骼，不是项目组里的「虚拟同事」。

- **治理特征**：无统一意图契约；无跨角色约束矩阵；无面向交付的 Agent 证据链。

- **典型遥测画像（参考）**：任务级遥测稀疏；首次成功率与自愈率不具备组织级统计意义。

- **跃迁信号（进入 L2）**：开始把可拆分任务**显式交给 AI 执行并回收结果**，而非仅在 IDE 里接受补全建议。

------

### 5.3 L2：人机编队期（Hybrid Agentic Scrum）

- **现状**：智能体以「虚拟员工 / 执行单元」身份进入项目组。人类仍主导迭代目标、优先级与对外承诺。

- **动作**：将一部分**边界清晰**的基础任务（单元测试、简单 CRUD、报表抽取、文档整理等）通过任务系统、对话工具或工作图（Work Graph）分发给 Agent。每日站会可弱化「纯信息同步」（由工具汇总状态），**保留障碍暴露与决策同步**。

- **说明**：不绑定某一品牌的工作流工具；关键是「任务可派发、结果可回收」，而非必须使用 Jira。

- **治理特征**：开始出现任务说明与检查清单，但往往缺少可执行约束与门禁；证据仍零散。

- **典型遥测画像（参考）**：有一定任务完成记录；人机往返次数偏高；MUST 类约束尚未系统化。

- **跃迁信号（进入 L3）**：引入 **IO / OA / AS** 分工，并让**契约—约束—证据**成为默认交付方式，而非偶发实验。

------

### 5.4 L3：受控自治期（Constrained Autonomy）

- **现状**：**执行权**从「会议驱动」转向「契约约束驱动」。传统 Scrum 仪式可保留、可裁剪，但**不再是唯一治理中枢**——关键门禁由约束矩阵、证据包与 HITL 裁决承担。

- **动作**：落地 **3-4-3 架构**。原 PO 类角色更多以 **IO（意图主理人）** 提出假设与边界；资深工程师等以 **OA（编排架构师）** 维护契约、约束、运行与证据验收；**AS（自治蜂群）** 在护栏内完成代码生成、测试与修复。Agentic Agile **仅接管**边界清晰、验证完备、风险可控的生成 / 测试 / 发布类任务。

- **说明**：不以「必须彻底废弃 Scrum」为意识形态门槛。若组织仍使用看板或冲刺，但 **意图契约、约束门禁、证据裁决** 已成常态，即可认定为进入 L3。

- **治理特征**：

  1. 存在可追溯的意图契约（任务级或等效工件）；

  1. 存在可执行或可审计的约束（含安全与质量底线）；

  1. 关键交付有证据包或等效验收记录；

  1. 角色职责可指认（谁拍板意图、谁守门禁、谁执行）。

- **运行遥测门槛（建议窗口：连续 ≥10 个已完成任务，或等效周期）**：

  - 首次成功率 ≥ 70%；

  - MUST 类约束失败率 ≈ 0（允许有记录的例外与修复闭环）；

  - 运行自主性得分（0–100）建议 ≥ 60（能力层综合分，含自愈、MUST 通过率、HITL 负担等）；

  - 无未关闭的高危安全项（或已有书面例外）。

------

### 5.5 L4：适应性治理期（Adaptive Agentic Governance）

- **现状**：向「意图即软件（Intent as Software）」演进——观测、意图调整与实现闭环显著缩短；人类工作重心移至**商业策略与 AI 治理**，而非逐行审码或逐会排期。

- **动作**：意图图谱与运行态（含发布证据、质量与业务信号）深度耦合。当数据表明目标偏离时，分析侧可提出意图调整建议，开发侧在约束内快速重构相关能力；人类在核心决策与风险敞口上 **Approve / Reject**。项目管理编制可大幅收缩，转化为「策略团队」与「AI 治理团队」。

- **可测化说明**：

  - **不把**「秒级自动改生产且零人审批」作为 L4 硬门槛；

  - **要求** HITL 以**价值与风险裁决**为主，而非默认逐任务人工返工；

  - **要求** 意图 / 契约 / 约束随交付持续反哺；发布与回滚路径可证明；

  - 生产写权限等不可逆操作仍须权限隔离与审批策略（与安全底线一致）。

- **运行遥测门槛（建议窗口：连续 ≥10 个任务，且含生产相关或高风险任务样本）**：
- 目标准确率 ≥ 90%；
  
- 约束自愈率 ≥ 80%；
  
- 运行自主性得分建议 ≥ 80；
  
- 低 HITL 连续段可统计（例如连续 N 个任务无「因能力不足导致的」强制升级）；

### 5.6 度量与遥测：不是第五个工件，而是治理反馈系统

度量回答“组织想判断什么”，指标定义表达口径，Telemetry 持续采集运行信号，Evidence Bundle 支持单次裁决，Dashboard 帮助人观察趋势并采取行动。3-4-3 采用四层九维模型：

| 层级 | 核心问题 | 主要维度 |
| :--- | :--- | :--- |
| 价值层 | 是否完成值得完成的事情 | 目标准确率、首次成功率、复合 ROI |
| 能力层 | Agent 能在多大范围可靠自治 | 约束自愈率、自主性综合评分 |
| 效率层 | 人、上下文、模型和编排是否高效 | 上下文压缩比、Token 效率、执行效率 |
| 进化层 | 经验是否改善下一次执行 | 知识沉淀率 |

每个 Intent Contract 都形成一份任务级遥测和 Dashboard，与 Evidence Bundle 对应；所有契约再聚合到全局 Dashboard。这样组织可以从项目趋势下钻到具体意图、证据、Agent 行为和 Token 成本。

古德哈特法则提醒我们：当指标成为强制目标，它可能失去原本意义。追求最低 Token 可能造成上下文不足，追求零 HITL 可能让 Agent 越过责任边界，追求最高首次成功率可能诱导团队隐藏 Bug。因此主指标必须与反指标、任务分群、数据来源和治理动作联读，遥测默认用于改善系统，不用于简单排名个人。

### 5.7 Agent Memory Engineering：从经验到可治理组织记忆

Loop Memory 维持跨 cycle 的进度、教训、风险、模式、开放问题和决策，但“被记住”不等于“成为知识”。一次失败首先只能形成候选记忆；经过真实证据、独立验证和责任人裁决后，才可以晋升为知识、约束、测试、Playbook 或 Skill。

可治理记忆至少需要来源、类型、作用域、版本、状态、权限和有效期。它应当可召回、可衰减、可冲突处理、可撤销，也能在源数据删除时传播删除要求。完整聊天、模型隐式推理、未经验证猜测和密钥不应进入长期组织记忆。

```text
任务状态 → 候选经验 → 证据验证 → 组织记忆
                              ↓
               知识 / 约束 / 测试 / Skill
```

## 六、最小落地蓝图：如何在 90 天内试出真伪？

如果 Agentic Agile 只能停留在概念层，它就只是另一套关于 AI 的修辞。真正的落地，必须从**小范围、强约束、可验证**的试点开始。

### 1. 试点准入条件（Pilot Entry Criteria）
建议组织只在同时满足以下条件时启动首个试点：

*   **任务边界清晰**：优先选择内部工具、BFF 服务、自动化脚本、报表服务、营销实验等边界明确的场景，而非核心交易主链路。
*   **验证链路存在**：至少具备基础 CI、自动化测试、静态检查、沙箱环境与回滚机制。
*   **业务 Owner 在场**：必须存在可持续响应的 IO，确保意图不是一次性输入后长期失真。
*   **仓库上下文可管理**：代码仓库具备最基本的 README、模块说明、权限边界与依赖治理文档。
*   **合规风险可隔离**：试点范围不直接触碰支付清结算、核心风控、隐私主数据、生产数据库写权限等高风险区域。

### 2. 最小角色责任矩阵（Minimal Governance Matrix）

| 工件/动作 | Responsible | Accountable | Consulted | Informed |
| :--- | :--- | :--- | :--- | :--- |
| 意图契约（Intent Contract）批准 | IO 起草 / 修订 | IO | 业务、架构、安全 | AS |
| 约束矩阵（Constraint Matrix）维护 | OA | OA | 安全、法务、平台 | IO、AS |
| 智能体执行与验证 | AS | OA | QA、安全 | IO |
| HITL 升级裁决 | OA 触发 | IO 或指定审批人 | 法务、架构、安全 | AS |
| 证据包验收 | OA 汇总 | IO | QA、平台 | 相关干系人 |

### 3. 最小工件闭环（Minimum Artifact Loop）
首个试点不需要“大而全”，但必须建立四大核心治理工件：

1. **Intent Graph**：连接试点目标、任务依赖、影响范围与完成后的组织学习。
2. **Intent Contract**：明确每个任务的业务目标、成功标准、非目标、风险边界并由 IO 签署。
3. **Constraint Matrix**：明确权限、预算、禁区 API、数据合规、质量门禁与升级条件。
4. **Evidence Bundle**：沉淀验收所需证据，而不是只交付代码 diff。

此外，用 **Work Graph / Execution Log** 记录编排、工具调用、关键决策与失败原因，用 **Telemetry Dashboard** 观察质量、成本、自治、升级和价值结果。前四项定义治理责任，后两类支撑运行与反馈，不能彼此替代。

### 4. HITL 触发条件（Mandatory Escalation Rules）
以下情况必须触发人类异常裁决协议，而不是继续让 Agent 自主迭代：

*   **契约不完整**：成功标准缺失、非目标未定义、边界条件冲突。
*   **预算异常**：Token、执行时长或工具调用次数连续超阈值。
*   **证据不足**：测试未覆盖关键路径，或验收证据无法支撑上线结论。
*   **权限越界**：涉及未授权系统、生产写权限、敏感数据访问。
*   **目标互斥**：增长、成本、合规、安全之间出现无法自动求解的冲突。

### 5. 证据包的最低组成（Minimum Evidence Bundle）
一份可进入审批环节的 Evidence Bundle，最低应包含：

*   **需求与非目标摘要**：本次变更解决什么，不解决什么。
*   **测试与验证结果**：单测、集成测试、回归测试、静态扫描结果。
*   **运行日志摘要**：关键工具调用、失败重试、升级节点。
*   **风险与回退方案**：已知风险、灰度策略、回滚条件。
*   **成本记录**：执行轮次、算力消耗、人工介入次数。

### 6. 90 天试点路径（90-Day Pilot Path）

90 天不是“必须达到 L3”的倒计时，而是一个可证伪的实验窗口。启动前必须写清：试点假设、4—8 周历史基线或对照样本、质量与安全护栏、成功阈值和提前停止条件。否则任何结果都可能被解释成成功。

*   **0-30 天——基线与最小闭环**：仅允许 Agent 处理低风险、强验证任务，完成 3—5 个真实样本；建立意图图谱、契约、约束与证据包，接入现有 CI/测试/沙箱，并主动验证 MUST 失败和越权是否会被阻断。
*   **31-60 天——扩大样本与验证恢复**：扩大到约 8—15 个任务，可加入单服务重构、接口/UI/SIT/性能测试；引入 Work Graph、重试上限、HITL 与回退，测量首次成功、自愈、人工投入、Token、逃逸缺陷和单位增量成本，防止成本转移给 QA 或业务。
*   **61-90 天——重复性与自治裁决**：保持指标口径不变，覆盖成功、自愈、升级和回退样本；按任务类型分别决定扩大、受限继续、先补工程基础或停止。只有当净收益稳定、质量安全护栏未恶化、验证和恢复可靠时，才扩大自主范围。

### 7. 试点平衡记分卡与退出条件

试点至少同时观察四组指标：

| 类别 | 代表指标 | 防止的误判 |
| :--- | :--- | :--- |
| 效果 | 目标准确率、首次成功率、周期、吞吐 | 只看代码生成速度 |
| 护栏 | MUST 失败、逃逸缺陷、回滚、高危安全事件、UAT 否决 | 把风险转移到下游或生产 |
| 成本 | 人工小时、Token、工具费用、等待与返工 | 只算 Agent 执行成本 |
| 学习与价值 | 知识/约束/测试/Skill 晋升及复用、业务结果 | 只完成一次演示，不能复制 |

发生重大越权、连续证据失真、质量护栏持续恶化、总成本显著高于基线，或业务 Owner 无法持续参与时，应暂停试点。能够用证据得出“该场景目前不适合”的结论，也是一次有效试点。

## 七、证据基础与验证框架：为什么它值得认真对待？

我们必须承认一个基本事实：**当前公开证据并不支持“自治代码生成会自动带来更好的工程结果”这一简单结论。** 现阶段更可靠的结论是：Agentic Agile在某些场景下能显著加速交付，但结果高度依赖流程控制、验证纪律、仓库上下文与权限治理。

### 1. 当前证据已经支持什么？

| 结论 | 证据状态 | 主要来源 | 对本文的含义 |
| :--- | :--- | :--- | :--- |
| Prompt 不是核心问题，流程控制才是关键问题 | 已有明确论述支持 | Koch (2026), Microsoft Blog (2026) | 支撑“契约机制、约束矩阵、证据包”是方法论核心，而非附属装饰 |
| Agentic 系统对不同任务的收益高度异质 | 已有摘要级与实践级支持 | Koch (2026) | 说明 Agentic Agile 必须按场景分级落地，不能假设对所有研发活动都同样有效 |
| 仓库级指令、文档和持久化项目记忆会显著影响稳定性 | 已有工程实践支持 | Microsoft Blog (2026), Agentic-Agile Template | 说明 `.github/copilot-instructions.md` 一类外化指令不是细节，而是治理基础设施 |
| Skill 模块化与工作流封装有助于复用、隔离与治理 | 已有工程框架支持 | agentic-engineering-framework | 说明 AS 不应是无结构的“大模型黑箱”，而应是可组合的执行单元 |

### 2. 当前证据尚未支持什么？

本文明确不把以下内容当作未经验证即可普遍成立的事实：

*   不把“4 小时替代 45 天”之类数字当成跨组织通用结论。
*   不把“缺陷下降 99%”或“成本下降 92%”当成无条件复用的宣传口径。
*   不把“全部研发活动都可以由 Agent 接管”视作近期现实。

这些数字若要进入企业内部汇报，必须来自本组织自己的试点数据，并附带任务类型、验证方式、约束条件与样本时间窗。

### 3. 企业试点应验证的核心指标

与其追逐外部故事，不如优先验证自身系统中的 6 个指标：

*   **契约一次通过率**：有多少需求能在首次澄清后进入执行。
*   **验证一次通过率**：Agent 产出在首轮自动化验证中通过的比例。
*   **HITL 升级频率**：每个意图平均触发多少次人工裁决。
*   **单位增量成本**：每个被接受的增量所消耗的 Token、时间与人工分钟数。
*   **回滚率**：进入灰度或上线后需要撤回的比例。
*   **意图到上线周期**：从 Intent Contract 批准到可部署增量产生的时间。

## 八、适用边界与反例：什么情况下不该强推 Agentic Agile？

一个成熟的方法论，不仅定义自己在哪些地方成立，也明确自己在哪些地方暂时不成立。

### 1. 暂不建议直接采用的场景

*   **高监管核心系统**：如清结算核心、核心风控决策、医疗诊疗主链路、航空航天控制系统。除非独立验证与审计能力先成熟，否则不应直接放大自治范围。
*   **缺乏业务 Owner 的团队**：如果没有稳定的 IO，Agent 只会加速把模糊意图放大成模糊产物。
*   **工程基础薄弱的组织**：没有测试、没有 CI、没有回滚、没有模块文档的团队，不适合直接跳到 Agentic Agile。
*   **无法自动验证的任务**：如果结果优劣无法被测试、规则或外部反馈快速判断，自治收益会显著下降。

### 2. 典型反例

*   **把 Agent 当外包团队**：只给一句模糊目标，期待系统自行补完全部上下文。
*   **先上自治，再补治理**：没有约束矩阵和证据包，直接要求自动提交、自动上线。
*   **把 OA 做成超级审批瓶颈**：如果所有决策都回到 OA 手里，系统就会退化成更昂贵的人工流程。

## 九、结语
Agentic Agile 不是对管理学的修补，而是对软件研发工程的**重构与再分层**。它真正改变的，不只是“谁来写代码”，而是“需求如何进入系统、约束如何对执行生效、证据如何替代感觉成为验收依据”。未来的组织中，谁能最高效地表达战略意图，谁能最稳定地掌控自治系统的边界与合规，谁就更有机会赢得下个十年的竞争优势。

## 十二、参考资料与延伸阅读 (References & Further Reading)

本白皮书的理论框架与工程实践规范，深度参考并融合了控制科学的经典底座，以及业界最前沿的学术论断与开源工程库。我们向以下先驱性的探索致敬：

### A. 经典控制论与系统学底座 (Classic System & Cybernetics Foundations)

1. **Ashby, W.R. (1956). *An Introduction to Cybernetics***.
   * **核心贡献**：提出控制论中的核心基石“阿什比法则（Law of Requisite Variety）”，即“只有多样性才能吸收多样性”。
   * **应用映射**：解释为什么治理系统需要足够多样的约束、验证、恢复和 Agent 能力来应对被治理系统的复杂性。
2. **Wiener, N. (1948). *Cybernetics: Or Control and Communication in the Animal and the Machine***.
   * **核心贡献**：定义了一切稳态系统必须依赖反馈机制消除偏差的基础规律。
   * **应用映射**：支撑 SCOPE-V 快内环、Telemetry 慢外环和基于反馈持续纠偏的控制结构。
3. **Miller, G.A. (1956). *The Magical Number Seven, Plus or Minus Two* & Dunbar, R. (1992)**.
   * **核心贡献**：确立了认知科学中人类短期工作记忆的容量限制与稳定社会网络的规模极限（邓巴数）。
   * **应用映射**：说明为什么上下文需要外化、任务需要裁剪、人的注意力应集中于价值与异常；这些理论不能被简单解释为 AI 已经消除了组织协作边界。

### B. 敏捷与智能体前沿工程实践 (Agile & Agentic Frontier Practices)

4. **Beck, K., et al. (2001). *Manifesto for Agile Software Development***.
   * **来源**：https://agilemanifesto.org/ （访问日期：2026-08-07）
   * **核心贡献**：20 年前定义了传统软件工程的协作精神。
   * **应用映射**：本白皮书宣言延续其重视价值、反馈、协作与适应的精神，并针对人机协作增加契约、治理与验证要求。
5. **Ng, Andrew. (2024–2026). *Agentic Design Patterns / Agentic AI***.
   * **来源**：DeepLearning.AI，[Agentic AI](https://www.deeplearning.ai/alpha/courses/agentic-ai)；[Agentic Design Patterns: Reflection](https://www.deeplearning.ai/the-batch/agentic-design-patterns-part-2-reflection)（访问日期：2026-08-07）。
   * **核心贡献**：系统性倡导“Agentic Workflow（智能体工作流）”，将反思（Reflection）、工具调用（Tool Use）等确立为标准范式。
   * **应用映射**：白皮书提出的“自治群智网络（AS）”的底层运作基础。
6. **Koch, C. (2026). *Agentic Agile-V: From Vibe Coding to Verified Engineering in Software and Hardware Development***.
   * **来源**：arXiv (https://arxiv.org/abs/2605.20456)（访问日期：2026-08-07）
   * **核心贡献**：系统性批判了“Vibe Coding（氛围编程）”由于缺乏约束而带来的工程灾难，提出了涵盖“Specify, Constrain, Orchestrate, Prove, Evolve, Verify (SCOPE-V)”的体系，并定义了对话至契约机制 (Conversation-to-contract gate) 及证据包验收模型。
   * **应用映射**：支撑 SCOPE-V、对话到契约门、风险自适应流程与 Evidence Bundle 验收模型。
7. **Epstein, Daniel / Microsoft for Developers. (2026). *Agentic-Agile: Why Agent Development Needs Agile (Not Just Prompts)***.
   * **来源**：https://developer.microsoft.com/blog/agentic-agile-why-agent-development-needs-agile-not-just-prompts/ （访问日期：2026-08-07）
   * **核心贡献**：提出“大模型开发失败更多源于协调不佳与规范不清，而非 Prompt 质量差”的判断，并强调项目级记忆与仓库级约束的重要性。
   * **应用映射**：说明规格、仓库级持久指令、增量交付、CI 与 Review Gate 对人机协作的重要性；外化指令是约束的一种载体，不等于完整 Harness。
8. **Microsoft. (2026). *Toward an Agentic-Agile Manifesto***.
   * **来源**：https://github.com/microsoft/agentic-agile-template/blob/main/MANIFESTO.md （访问日期：2026-08-07）
   * **核心贡献**：从规格契约、人机伙伴关系、并行独立、内建治理和持续度量五个方面提出 Agentic-Agile 价值观，并明确它是对敏捷价值的演进而非替代。
   * **应用映射**：启迪与完善了白皮书内 Agentic Agile 宣言的立论视角。
9. **Microsoft. (2026). *Agentic-Agile Template***.
   * **来源**：GitHub (https://github.com/microsoft/agentic-agile-template)（访问日期：2026-08-07）
   * **核心贡献**：将敏捷过程价值与 AI 编码智能体能力结合的官方实践模板库与脚手架。
   * **应用映射**：佐证了白皮书中关于人机编队落地（L2/L3 成熟度阶梯过渡）的实践可行性。
10. **Wei, D. Y. (2026). *agentic-engineering-framework***.
    * **来源**：GitHub (https://github.com/davidYichengWei/agentic-engineering-framework)（访问日期：2026-08-07）
    * **核心贡献**：基于 Skill 的模块化 Agentic Engineering 框架。提供了完整的 SDLC Workflow、最佳实践与 Self-Refinement 机制及定制指南。
    * **应用映射**：说明 Skill、Workflow 和项目知识如何提高 Agent 行为稳定性与可复用性，但不能消除底层模型的概率性。

### C. 度量治理与指标解释

11. **Goodhart, C. A. E. (1975). *Problems of Monetary Management: The U.K. Experience*.**
    * **核心贡献**：揭示当观察指标被转化为控制目标后，指标与原目标之间的关系可能失真。
    * **应用映射**：支撑主指标与反指标联读、禁止用单一 Token/HITL/成功率排名个人等度量纪律。
12. **Campbell, D. T. (1976). *Assessing the Impact of Planned Social Change*.**
    * **核心贡献**：说明定量指标承担的决策压力越大，越容易遭到操纵并腐化其所监测的过程。
    * **应用映射**：支撑试点基线、数据来源、任务分群、护栏指标与退出条件。
