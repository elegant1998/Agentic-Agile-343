## 0. 五类证据分类

证据包应覆盖以下五类证据。入门不必一次全覆盖，但**高风险结论不能只依赖单一、同源证据**。

| 类型 | 回答的问题 | 示例 | 本包覆盖 |
|------|-----------|------|----------|
| **意图证据** | 做的是不是已确认的事？ | 契约版本、规则来源、IO 确认 | §1 构建标识 + §2 目标 |
| **变更证据** | 实际改了什么？ | Git diff、文件清单、排除范围确认 | §1 + 变更范围确认 |
| **行为证据** | 功能是否满足 AC？ | 测试、接口记录、演示结果 | §4 测试 + §5 覆盖率 |
| **约束证据** | 红线是否被执行？ | 权限日志、扫描、门禁、审批 | §3 约束符合性 |
| **运行与价值证据** | 消耗和实际结果如何？ | Token、时长、失败率、用户指标 | §10 人工介入与成本 |

### 证据强度应匹配风险

同一个"通过"在不同场景下需要不同证据：

| 变化类型 | 风险特征 | 合理证据 | 裁决方式 |
|---------|---------|---------|---------|
| 文案调整 | 低（易发现、易恢复） | 预览 + 人工确认 | 自动检查或快速浏览 |
| 普通业务接口 | 中（可能误伤用户） | 自动测试 + 正反例 + 代码评审 | 自动检查后负责人确认 |
| 权限/隐私/资金/生产写 | 高（部分不可逆） | 独立安全验证 + 审计记录 + 受控环境 + 明确审批 | 人类核对关键证据后决定 |

> 不要为了形式堆积证据。每项证据都应能支持一个具体判断。

## 11. 建议裁决

```
approve | approve_with_conditions | return | reduce_scope | stop | request_clarification | escalate
```

| 裁决选项 | 含义 | 适用场景 |
|---------|------|---------|
| `approve` | 证据足以支持当前范围 | 全部 AC + MUST 通过，无未覆盖风险 |
| `approve_with_conditions` | 限定环境/用户/流量后放行 | 核心功能通过但需灰度验证 |
| `return` | 证据不足，返回指定阶段补充 | AC 有 fail 或 unknown |
| `reduce_scope` | 缩小意图契约后继续 | 部分功能完成，部分超范围 |
| `stop` | 风险或价值不再支持继续 | 方向错误或成本超预算 |
| `request_clarification` | 业务或技术问题需要新的权威输入 | 规则歧义、业务策略未确认 |
| `escalate` | 系统无法自行决定，提交 IO/OA | 影响范围不明、约束冲突 |

**建议裁决**: `__________`

**依据**: [一句话理由]

> **硬门禁**: 只要任一 MUST 为 FAIL/UNKNOWN，建议裁决不得为 `approve`。
> 存在 ESCALATE 状态的约束时，建议裁决应为 `escalate`。

## 11.5 人工审查清单（不确定验证）

> **定位**: 自动化测试覆盖的是"已知的已知"。
> 本章覆盖的是"已知的未知"——必须由人类站在 AI 看不到的角度审视。
>
> OA 在提交证据包给 IO 前，逐项确认。任何一项为"否"，不得标记 READY_FOR_HITL。

### 逻辑审查

自动化测试全部通过 ≠ 算法思路正确。

- [ ] 核心算法的设计思路是否经得起推敲？（不只看测试结果，看实现逻辑）
- [ ] 是否存在"测试通过但逻辑错误"的可能？（例如：测试用例恰好避开了边界条件）
- [ ] 状态机/流程引擎的转换是否完备？（所有状态都有定义，不存在隐式状态）
- [ ] 是否存在静默失败路径？（异常被捕获但未正确处理）

### 边界情况审查

自动化测试往往覆盖不到极端条件。

- [ ] 空数据场景是否处理？（空列表、null 值、0 值、空字符串）
- [ ] 并发场景是否考虑？（同时操作同一资源的结果是否可预期）
- [ ] 数据量边界是否验证？（最大/最小输入、超长字符串、特殊字符）
- [ ] 外部依赖不可用时系统如何表现？（数据库断连、第三方 API 超时）

### 上下文敏感审查

AI 可能没有获取最新的业务上下文。

- [ ] 当前业务策略是否有重大调整？（最近的业务决策是否已体现在代码中）
- [ ] 是否依赖了已废弃的接口或数据源？
- [ ] 是否有即将上线的功能与本任务产出冲突？
- [ ] 第三方依赖的版本/API 是否有 breaking change？

### 审查结果

| 审查维度 | 审查人 | 结果 | 发现的问题 |
|---------|--------|------|-----------|
| 逻辑审查 | [OA] | ✅ / ❌ | [如有] |
| 边界情况 | [OA] | ✅ / ❌ | [如有] |
| 上下文敏感 | [OA] | ✅ / ❌ | [如有] |

> **判定**: 三项全部 ✅ → 可进入 §12 最终裁决。任一 ❌ → 补充证据或回退修复。

## 12. HITL 裁决记录

> 裁决不是简单的 Approve / Reject。裁决者可从以下 6 种选项中选择，并必须关联证据和版本。

### 裁决选项

| 选项 | 含义 | 裁决者 | 后续动作 |
|------|------|--------|---------|
| **Approve** | 证据足以支持当前范围 | IO | 标记完成，进入下一任务 |
| **Approve with conditions** | 限定环境/用户/流量后放行 | IO | 记录限定条件，灰度验证 |
| **Return** | 证据不足，返回指定阶段补充 | OA | 回到 Orchestrate/Prove 阶段 |
| **Reduce scope** | 缩小意图契约后继续 | IO | 契约升级版本，移除超范围 AC |
| **Stop** | 风险或价值不再支持继续 | IO | 记录终止原因，归档 |
| **Request clarification** | 需要新的权威输入 | IO/OA | 收集澄清后重新进入 Specify |

### 结构化裁决记录

```yaml
hitl_decision:
  evidence_bundle: "EVID-XXX-001"          # 关联证据包 ID
  decision: "reduce_scope"                  # 见上方 6 种选项
  decided_by: "IO"                           # 裁决者角色
  rationale: "验证邮件策略尚未确认，本轮只完成账户创建能力"  # 必须填写理由
  required_changes:                          # 仅 return / reduce_scope 时填写
    - "意图契约升级为 1.1，将验证邮件列为 Non-goal"
    - "重跑受契约变化影响的 AC 映射检查"
  conditions:                                # 仅 approve_with_conditions 时填写
    - "限定测试环境使用"
    - "流量上限 10%"
  valid_until:                               # 裁决有效期
    intent_contract_version: "1.1"
```

> **裁决必须关联证据和版本**。否则一句"同意上线"无法说明批准了哪个范围、基于什么依据。
